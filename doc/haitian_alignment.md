# 海天杯环境对齐说明

## 1. 对齐口径

本项目新增可执行场景 `haitian_2026`。它依据
`doc/前置约束.md` 对资源、流程、海况和故障生命周期进行对齐，同时把原材料未给出的参数显式记录为建模假设。

该场景是“可追溯的假设对齐”，不是官方仿真器的逐行复刻。旧场景
`project_core` 仍为默认值，历史实验不传 `--scenario-profile` 时行为不变。

## 2. 已实现约束

| 类别 | `haitian_2026` 实现 |
| --- | --- |
| 飞机 | 总库存 75 架；甲板 45 架；A/B 两组各 20 架；甲板备份 5 架 |
| 波次 | A/B 交替；默认每 120 分钟一个波次 |
| 停机位 | 45 个，保留空间甲板图、路径占用和干涉约束 |
| 放飞 | 4 个物理起飞位；单一串行放飞通道；基础作业时间 1 分钟/架 |
| 回收 | 1 条回收通道；基础作业时间 1 分钟/架 |
| 加油 | 20 个固定加油站；每站覆盖 2 个任务机位；作业时间 `N(20, 3)` 分钟；每架占 4 名保障人员 |
| 人员 | 150 名保障人员按三班解释为 50 个同时在岗岗位；启用共享人员容量约束 |
| 例检 | 原材料没有每架次强制例检，因此对齐场景关闭旧的 `N(8, 1)` 例检 |
| 弹药提取 | 10 辆弹药转运车；5-10 分钟均匀分布 |
| 下层运输 | 6 部下层武器升降机；`N(3, 0.5)` 分钟 |
| 上层运输 | 4 部上层武器升降机；`N(3, 0.5)` 分钟 |
| 挂弹 | 10 辆挂弹车；逐枚 `N(5, sqrt(2))` 分钟；弹量概率为 1/2/3/4 枚对应 0.3/0.4/0.2/0.1 |
| 牵引 | 10 辆牵引车；继续使用时空路径预约和冲突检测 |
| 飞机升降机 | 2 部；故障飞机下送和备机上送共享容量 |
| 随机故障 | 每架飞机按指数 MTBF=100 飞行小时建模；只累计实际空中分钟数 |
| 维修 | 1-6 小时截断指数衰减分布；故障飞机进入机库、备机替换、修复后回到机库库存 |
| 海况 | 实现四档放飞等待概率、回收成功率和 6 级以上禁飞禁降 |
| 动态扰动 | 保留保障设备失效、跑道关闭、飞机 hold、飞机故障和服务减速 |

## 3. 显式假设

原材料缺失下列参数，当前配置采用：

1. 加油时间标准差为 3 分钟。
2. 上、下层武器升降机时间标准差均为 0.5 分钟。
3. 逐枚挂弹时间方差为 2 分钟平方。
4. 维修时间采用区间 `[60, 360]` 分钟、尺度 120 分钟的截断指数分布。
5. 故障频率解释为每架飞机的指数 MTBF，而不是全机队固定周期。
6. 回收失败后的复飞等待为 1 分钟，不额外建模燃油消耗。
7. 机库转运时间为 5 分钟；两部飞机升降机共享上下行任务。
8. 20 个加油站覆盖 0-39 号任务机位；40-44 号初始备份机位没有直接加油能力。回收优先选择有加油覆盖的机位。
9. 挂弹人员数、装配区容量、弹药型号兼容和库存未给出，因此不额外虚构人员或库存约束。
10. 维修时长从故障检测时开始计时，但修复完成还要求故障机已进入机库。

所有假设同时写入 `ScenarioProfile.unresolved_parameters` 或
`ScenarioProfile.metadata`，可随 manifest 导出。

## 4. 尚未精确对齐

以下信息需要官方数据才能进一步收敛：

- 45 个停机位、20 个加油站和两部飞机升降机的真实覆盖矩阵；
- 4 个起飞位中位于着舰区的两个位置与回收跑道的精确互斥关系；
- 真实甲板坐标、边权、滑行速度和自主滑行规则；
- 人员连续工作 4 小时、工作 8 小时后的疲劳与休息规则；
- 弹药装配区、型号、库存和挂弹人员约束；
- 复飞优先级、等待时间和燃油模型；
- 维修衰减函数的官方参数。

## 5. 运行方式

旧环境控制组：

```bash
python -m scripts.run_publishable_benchmark \
  --scenario-profile project_core \
  --phase dev \
  --seeds 43001 43002 43003 43004 43005 \
  --profiles none compound_light compound_medium compound_heavy \
  --intervals 57.5 \
  --budgets-ms 50 \
  --solvers heuristic cp_sat rl risk_aware_rl_cp \
  --waves 12 \
  --rl-checkpoint checkpoints/rl_multiload_bc.pt \
  --output-dir outputs/haitian_matched_project_core_5
```

对齐环境使用相同命令，仅替换：

```text
--scenario-profile haitian_2026
--output-dir outputs/haitian_matched_aligned_5
```

本轮 RL checkpoint 在旧 `project_core` 环境训练。对齐环境结果属于零样本迁移诊断，不能替代在
`haitian_2026` 上重新训练后的正式算法结论。

## 6. 五种子匹配诊断

诊断设置为开发种子 `43001-43005`、波次间隔 57.5 分钟、12 波次、四种扰动等级和
50 ms CP-SAT 预算。每个场景运行 5 seeds x 4 profiles = 20 个样本。

| 求解器 | `project_core` 平均架次 | `haitian_2026` 平均架次 | 变化 |
| --- | ---: | ---: | ---: |
| Heuristic | 109.35 | 76.60 | -32.75 |
| RL | 113.95 | 80.80 | -33.15 |
| CP-SAT | 114.45 | 82.20 | -32.25 |
| Risk-aware RL-CP | 114.60 | 82.15 | -32.45 |

在旧控制组中，Risk-aware RL-CP 相对 CP-SAT 为 `+0.15` 架；在对齐环境中变为
`-0.05` 架，bootstrap 95% CI 为 `[-0.45, 0.35]`。对齐环境中 Risk-aware
RL-CP 相对纯 RL 为 `+1.35` 架，相对 Heuristic 为 `+5.55` 架。

该结果只用于验证环境迁移后的算法行为：

- 旧 checkpoint 在对齐环境中仍能合法运行；
- 风险门控仍可弥补部分纯 RL 性能损失；
- 旧环境上相对 CP-SAT 的微弱优势不能迁移到对齐环境；
- 5 seeds 不足以形成投稿结论，正式结果必须在 `haitian_2026` 上重新训练后使用冻结种子复评。
